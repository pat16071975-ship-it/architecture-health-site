# AZ-BAZE — обязательный контракт всех загрузок

Этот контракт обязателен для текущих и будущих загрузок данных в AZ-BAZE.

## 1. До изменения данных

- Сначала полностью прочитать и проверить все выбранные файлы/даты.
- Проверить совпадение периода и обязательных источников.
- Проверить дубли и право на замену.
- Не изменять БД частично, пока весь комплект не прошёл preflight.

## 2. Запись

- Все связанные изменения одной загрузки выполнять в одной транзакции.
- При любой ошибке делать rollback всей операции.
- Идентичный повторный комплект не начислять повторно; писать в журнал `duplicate`.
- Замена ранее сохранённых отличающихся данных разрешается только отдельным правом.
- Пересборка отчёта не имеет права удалять независимые/ручные поля payload. Управляемые загрузчиком поля обновляются, остальные сохраняются.
- `marketingSources` и дата их актуальности переносятся вперёд до следующего подтверждённого снимка и не стираются ежедневной пересборкой.
- Общие `primary` и `repeat` должны совпадать с суммой Стоматологии и Отделения структуры. Неразнесённые строки исходного файла не прибавляются молча к управленческим итогам, а сохраняются отдельно в `_uploadControl` для контроля.

## 3. После записи

- Записать результат в журнал загрузок и аудит.
- После успешного сохранения пользователь обязательно получает крупное модальное окно с явным итогом и кнопкой `OK`.
- Для успешной загрузки заголовок: `ДАННЫЕ ЗАГРУЖЕНЫ`.
- Для замены: `ДАННЫЕ ЗАМЕНЕНЫ`.
- Для идентичного дубля: `ДУБЛЬ — ДАННЫЕ НЕ ИЗМЕНЕНЫ`.
- Для ошибки: `ЗАГРУЗКА НЕ ВЫПОЛНЕНА`.
- Модальное окно результата не закрывается автоматически: пользователь должен явно нажать `OK`.
- На время отправки формы кнопка загрузки блокируется и показывается состояние `ЗАГРУЗКА…`, чтобы исключить повторный клик.

## 4. Интерфейсный стандарт

Базовый шаблон `templates/base.html` содержит единый механизм `AZUploadFeedback` и автоматически включает состояние загрузки для форм с файловыми полями. Серверный экран загрузки должен передавать результат через маркер `data-az-upload-feedback`.

Новые экраны загрузки не должны создавать собственные несовместимые уведомления, если для этого нет отдельного утверждённого решения.

## 5. Проверка перед выпуском

Для любого нового или изменённого импортера проверить минимум:

1. успешную загрузку;
2. идентичный дубль;
3. ошибочный комплект без частичной записи;
4. замену с правом и отказ без права;
5. сохранность независимых полей payload;
6. согласованность агрегатов с детализацией;
7. журнал/аудит;
8. крупное итоговое модальное сообщение;
9. повторное открытие страницы без повторного выполнения операции.

## 6. Денежный источник «Счета и оплаты»

- Для обычной оперативной загрузки используются три источника: «Завершённые приёмы», «Выполненные услуги», «Счета и оплаты».
- «Завершённые приёмы» остаются источником посещаемости и первичных/повторных приёмов.
- «Выполненные услуги» остаются источником состава услуг, врача, групп услуг и «Аналитики услуг».
- «Счета и оплаты» является источником фактически принятых денежных средств.
- Факт = только положительное «Движение ДС» по ККМ ООО 0531380019042729 и ККМ ИП 0463880019042725.
- Отрицательное «Изъятие ДС» не уменьшает Факт: это внутреннее перемещение наличных для внесения на расчётный счёт.
- Движение без двух утверждённых ККМ не включается в Факт.
- «Выставлено счетов» считается отдельно и не подменяет Факт.
- Денежные поступления без достоверной связи с врачом/направлением входят в общий Факт, но не распределяются предположительно.
- Исторический файл «Счета и оплаты» разрешено загрузить отдельно для пересчёта денежных полей уже существующих отчётов; такая операция не должна изменять приёмы и «Аналитику услуг».
