# IDENT-004 — универсальная выгрузка IDENT

**Статус: SOURCE-ONLY кандидат для независимой проверки.**

Проект пилотирования: «Архитектура здоровья». Коммерческое назначение: MD Control. Отдельный коммерческий продукт и новый репозиторий не создаются. Этот пакет — переносимый локальный прототип, не установка и не релиз. Исходники размещаются в отдельной ветке AZ BAZE. В действующие приложения и базы AZ BAZE, MD MOS и MD Control изменения не вносятся.

## 1. Назначение и подтверждённые источники

Прямой доступ к MS SQL IDENT в режиме чтения и выполнение агрегирующего SELECT по `dbo.PaymentsIn` подтверждены оператором 25.11.2026. Метаданные получены для 269 объектов, в том числе 22 предметных таблиц/представлений. Права SELECT для этих 22 объектов подтверждены. Это не доказывает отсутствие всех прочих прав учётной записи и не гарантирует полноту всех будущих отчётов.

Первый набор `payments_daily_v1` опирается только на подтверждённые столбцы `PaymentsIn.DatePayment` (date), `ID_Patients` (int) и `Payment` (decimal), все NOT NULL. Точная precision/scale будет прочитана в предзапусковой проверке. Метаданные пациента, ФИО, телефоны, индивидуальные платежи и сведения медицинской карты не выгружаются. В пакете только синтетические примеры и имена объектов схемы; реальные адреса, пароли, идентификаторы клиники и суммы клиники отсутствуют.

`PaymentsIn` не имеет RowVersion в исследованной схеме, но имеет DateTimeAdded/DateTimeChanged (nullable). Не используем MAX(ID) или одну дату последнего изменения как достаточный механизм обнаружения исправлений и удалений.

## 2. Архитектура (предложение к реализации после приёмки)

IDENT MS SQL -> Windows collector (только SELECT) -> закрытая локальная очередь -> защищённый HTTPS -> приём и журнал пакетов -> нормализованное хранилище -> потребители.

- В пилоте потребитель AZ BAZE. Данные поступают в отдельную теневую витрину, не заменяют активные Excel-источники без сверки и разрешения.
- MD Control получает библиотеку проверенных SQL-профилей, версионированные форматы, тесты и семантику показателей; не реальные данные пилотной клиники. Используются существующие изолированные установки MD Control (customer_hosted / managed_subscription), DataSource и SourceAdapter; отдельный вариант для каждой клиники не кодируется.
- MD MOS получает отдельный адаптер потребления по мере готовности разделов. Миграция пациентов и записей не входит в первый финансовый профиль.
- Адрес SQL, имя/порт, учетная запись, source_id, идентификатор потока, часовой пояс, настройки филиалов, направления, кассы, календарь и периодичность — настройки, не константы в бизнес-логике.
- Для будущего транспорта сервер удостоверяет источник и организацию по защищённой учётной записи агента, а не по присланному JSON. Каждый источник/поток однозначно привязан к разрешённой организации и области данных. Регистрация и смена потока — отдельное контролируемое действие.

## 3. Контракт пакета v1

Кодировка UTF-8, JSON без BOM. Максимум 512 КиБ и 31 календарный день в одном пакете (временные технические ограничения прототипа, не утверждённые продуктовые лимиты). Поля строго по белому списку, неизвестные поля и дубли JSON-ключей отклоняются.

Обязательные поля верхнего уровня:

- `contract_version=1`, `dataset=payments_daily_v1`, `scope=whole_source_database`.
- `source_id` и `stream_id` — зарегистрированные UUID, не имя клиники, логин или IP; `batch_id` — отдельный UUID; `sequence` — возрастающий номер наблюдения в пределах потока. В прототипе это ручной номер, не дата платежа. В будущей службе — сохраняемая последовательность, один активный автор потока и контроль перерегистрации.
- `source_timezone` — IANA timezone организации (даты DatePayment остаются локальными календарными датами источника).
- `date_from` включительно, `date_to_exclusive` исключительно. Строгий YYYY-MM-DD.
- `query_started_at`, `observed_at` — UTC ISO 8601. Времена фиксируют наблюдение, а не очередность доставки. `coverage=full_query_window_as_observed`: успешное чтение выбранного окна; текущий день может быть незавершённым, это не гарантия согласованного снимка всех таблиц или закрытия дня.
- `query_sha256` — SHA-256 текста профиля с LF, UTF-8 без BOM. Это проверка версии контракта, а не криптографическое доказательство фактического исполнения SQL; происхождение в рабочем продукте требует доверенного сборщика и аутентификации.
- `schema` — фактические precision и scale столбца Payment, закрепляются при первом принятом пакете; изменение блокирует следующие пакеты до проверки совместимости.
- `rows` — по одной строке на каждую дату, в порядке возрастания. Только после полного успешного SELECT отсутствующие даты заполняются нулём; ошибка SQL/timeout/несовместимость не создают нулевой отчёт.

Состав строки: `date`, `records_count`, `paying_patients`, `positive_amount`, `negative_amount`, `net_amount`.

Суммы хранятся как точные десятичные строки с точкой, без float, экспоненты или разделителей тысяч. Валидатор проверяет знак, масштаб, суммарный баланс `positive_amount + negative_amount == net_amount`, `paying_patients <= records_count`, наличие положительного платежа при положительном количестве пациентов и согласованность нулевой строки. Количество пациентов — distinct ID с положительной записью за день; складывать эти количества для получения уникальных пациентов за месяц нельзя. Для уникальных пациентов за период необходим отдельный проверенный профиль.

Область первого профиля — вся конкретная БД. Он не распределяет показатели по филиалам. До реальной выгрузки необходимо подтвердить, что чтение всей этой БД разрешено для пилотной организации. Для многоклинических источников нужен отдельный профиль с проверенным фильтром `ID_OwnCompanies` и авторизованным сопоставлением подразделений. Этот фильтр не добавлен скрыто в уже проверенный запрос.

## 4. Надёжность и журнал

Приёмник создаёт отдельную SQLite только по явному вызову init, с собственным application_id и версией. Отказывается изменять уже существующую чужую базу. Привязку source/stream/timezone не меняет. Новые пакеты проходят целостную валидацию до публикации. В одной транзакции сохраняются точные исходные байты, их SHA-256 и актуальные значения по датам; сбой отменяет обе записи. Дневная витрина заменяется только в покрытом диапазоне. Дубликат тех же байтов и номера подтверждается без повторного изменения данных. Конфликт UUID или sequence, чужой поток, неполное окно, несогласованные деньги, изменившаяся схема и устаревший пакет с пересечением более новой даты отклоняются. Старый непересекающийся период допустим.

Нулевая строка — результат успешного запроса, а не пропавшего соединения. История пакетов остаётся в отдельном хранилище. Приёмник — не продуктивный многопользовательский сервис; нет HTTP, управления токенами, политики архивной ретенции, зашифрованной дисковой очереди, резервного копирования и мониторинга.

## 5. План регулярной выгрузки (IDENT-005/006; отдельно утверждается)

1. Определить выделенный компьютер, сетевой доступ и подтверждённый режим TLS: стандартная цепочка доверия или явно закреплённый сертификат. Во всех режимах обязательны шифрование и проверка сертификата; `TrustServerCertificate=False`. Для рабочей службы не применять диагностический обход TLS. Первичное подтверждение подлинности закрепляемого сертификата и фактическая проверка подключения — обязательные условия допуска. Пароли хранить локально под ограниченной служебной учётной записью (Windows Credential Manager / DPAPI либо утверждённое хранилище); не помещать в Git, аргументы команд, конфиги выгрузки и логи.
2. Проверить SELECT и эффективные права записи, версию SQL, индексы, режим согласованности чтения, задержки и нагрузку. Не менять БД, включать CDC/Change Tracking, добавлять индексы или конфигурировать изоляцию без разрешения. Не применять NOLOCK. Если READ_COMMITTED_SNAPSHOT не включён, отдельная проверка согласованности и влияния конкурирующих транзакций необходима; один SELECT не равен доказанному согласованному снимку всех данных.
3. Выполнить один ручной тест за короткий интервал (сначала один день / три дня по решению владельца) и получить агрегаты. Сопоставить с ранее выполненным запросом для того же фактического состояния базы и отчётом IDENT.
4. После измерения нагрузки — выбрать расписание: предварительное предложение для оплат каждые 5 минут, повторное чтение текущих дней и скользящего окна, ночью циклическая сверка исторических периодов, ручной повтор диапазона. Число дней и частота утверждаются после проверки; исправления вне короткого окна обнаруживаются только в последующей исторической сверке. Курсор только по ID не применяется.
5. Windows-служба: эксклюзивная блокировка сборщика, надёжно сохраняемый номер/эпоха, локальная атомарная очередь, повторная передача точно тех же байтов до подтверждения (ACK с batch_id и хешем после долговечной записи), ограниченные повторы с backoff, лимит диска, сигнал ошибки, безопасная остановка. Перезапуск не обнуляет номера. Восстановление БД/смена источника требует сверки и контролируемой смены потока. Данные в очереди не удаляются по одному сетевому HTTP 200 без сверки ACK.
6. Сервер: защищённый endpoint, авторизация источника/организации/набора данных, ограничения размера и частоты, атомарное принятие, журнал/heartbeat/last-success, закрытые резервные копии, отдельная теневая витрина AZ BAZE. Сетевой SQL-порт IDENT наружу не открывается.
7. До активации каждого показателя — сравнение с отчётом IDENT, единицами, фильтрами, периодом, возвратами, авансами и исправлениями. Старая активная отчётность не суммируется с новой. При несовпадении сохраняются обе версии, отчёт остаётся на старом источнике до решения владельца.

Для других сущностей выбирать механизм по их метаданным: `RowVersion` есть, например, у Persons и Receptions, но он не временная метка, не фиксирует удаления и требует проверки безопасной верхней границы чтения. Не внедрять простое чтение MAX(RowVersion). Стратегия SQL Server MIN_ACTIVE_ROWVERSION и удалений подлежит отдельному проектированию. Где RowVersion нет, нужна проверенная стратегия периодического повторного чтения/сверки, а не угадывание по nullable DateTimeChanged.

## 8. Будущая миграция в MD MOS (вне текущей дельты)

- Идентичность сущности в обмене: `source_id + entity_type + external_id`, привязка к разрешённой клинике и внутреннему ID MD MOS отдельно. Для пациентов проверить `Patients.ID_Persons = Persons.ID`, ExternalUID и фактические FK/уникальность. Телефон и ФИО — поиск кандидатов, не ключ автоматического слияния (общий семейный телефон разрешён в MD MOS). Статусы и форматы дат рождения подлежат сопоставлению. Не переносить все поля SELECT *.
- Отдельный режим предварительного просмотра/сверки и авторизованный серверный импорт через действующий механизм идентичности MD MOS, без обхода прав и без изменения действующих карточек автоматически. Конфликт, удаление, объединение и смена источника истины для каждого раздела — отдельные правила. MEDICAL и PII только после утверждения состава данных, прав доступа, хранения, согласованного контура и мер защиты. Никогда не выгружать паспорта/СНИЛС/медицинские карты в логи или тесты по умолчанию.
- Приёмы: Receptions, план/факт/отмена/перенос. Не считать запись автоматически завершённым приёмом. Расписание: CurrentTimeTable + справочники Times/Armchairs и Staffs, требуется отдельная проверка. Счета/услуги/оплаты/возвраты — отдельные датировки и связи. ЗТЛ и медрасходка — после изучения метаданных и сверки.

## 9. Локальное воспроизведение (только искусственные данные)

```bash

  --source-id 11111111-1111-4111-8111-111111111111 \
  --stream-id 22222222-2222-4222-8222-222222222222 \

```

Ожидается `STORE_READY`, `ACCEPTED`, `ALREADY_ACCEPTED`. Не использовать путь к действующим БД. CLI предназначен для частного локального каталога, не открытого общего ресурса; права каталога в реальном развёртывании проверяются отдельно. В рабочем контуре коллектора потребуется подписанное/контролируемое распространение SQL-профилей и кода, отдельное управление доступом к очереди. Текущий комплект не устанавливает зависимости и не выполняет команды автоматически.

Не защищаем от администратора/SYSTEM, процессов той же учётной записи, компрометации хоста и смены конфигурации привилегированным субъектом. ## 12. IDENT-004-TLS — дополнение SOURCE-ONLY от 26.11.2026

Причина: при диагностике на пилотной машине SQL Server предъявил автоматически сгенерированный самоподписанный сертификат. Владелец отказался менять настройки исходного SQL Server. Реальные адрес, идентификаторы и отпечатки сертификата не включены в исходники. Никаких изменений на серверах, в Windows, IDENT и приложениях не выполняется.

### Режимы

- `Standard` (по умолчанию): прежний System.Data.SqlClient в Windows PowerShell 5.1, Encrypt=True, TrustServerCertificate=False, нормальная проверка цепочки и имени. Передача pin-параметров в этом режиме — STOP.
- `PinnedCertificate` (только явно): отдельный процесс Microsoft.Data.SqlClient 7.1.2, Encrypt=Mandatory, TrustServerCertificate=false, ServerCertificate=<абсолютный путь к заранее утверждённому DER>. Не применяем Strict/TDS 8.0 без проверки поддержки конкретным SQL Server. В этом режиме доверие строится на точном совпадении сертификата, а не на принятии любого самоподписанного сертификата, имени CN или одного SHA-1 отпечатка. Без pin или при ошибке нет автоматического перехода на иной режим.
- В обоих режимах `-ConnectionCheckOnly` после успешной проверки TLS, базы, эффективных прав и метаданных завершает работу до финансового SELECT и формирования файла. Это не тест достоверности финансов.

### Контракт сборки и запуска кандидата

Выбран отдельный исполнитель net10.0 / win-x64, чтобы не менять системный SQL-драйвер и версию PowerShell пилотного компьютера. Исходный стандартный режим сохранён. NuGet-пакет Microsoft.Data.SqlClient задан точной версией [7.1.2], включён аудит всех зависимостей и остановка при указанных предупреждениях. NuGet.Config задаёт официальный источник. В проект как embedded resources включены непосредственно три существующих SQL-файла, не новые копии запросов.

На разрешённом сборочном контуре: восстановить зависимости с точным NuGet.Config и сформировать packages.lock.json; проверить зависимости, происхождение, lock, результаты NuGet-аудита, SDK и самодостаточную сборку. Выпускать только после повторной сборки с --locked-mode и проверки опубликованного файла. Команда сборки после lock: dotnet publish sql-client/IdentSqlReader.csproj -c Release -r win-x64 --self-contained true --no-restore. Отдельное разрешение требуется для сборки/публикации установочного артефакта и его установки. Кандидат рассчитан на один проверенный IdentSqlReader.exe, без незакреплённых внешних DLL. Если фактическая публикация требует дополнительных файлов, текущий способ поставки не допускается до дополнительной проверки. В этой дельте lock и исполняемый файл не создавались, сборка .NET не выполнена.

Пилотная структура внутри уже предусмотренного защищённого PrivateOutbox:
- connection/IdentSqlReader.exe — одобренный бинарный файл, SHA-256 указывается явно через PinnedWorkerSha256;
- connection/server.cer — точный публичный DER-сертификат, SHA-256 указывается через PinnedCertificateSha256;
- connection/bundle-cache/ — отдельный заранее подготовленный закрытый каталог для извлечения нативных компонентов самодостаточной сборки; не использовать чужое/непроверенное содержимое.

Каталоги и оба файла должны пройти ранее утверждённые проверки NTFS/ACL/сетевых общих ресурсов, reparse points и владельца. Родитель проверяет SHA-256 исполняемого файла до запуска и удерживает читающий дескриптор. Исполнитель повторно проверяет локальный сертификат, его точные DER-байты, отсутствие private key, SHA-256 и срок действия, удерживает файл без разрешения записи/удаления до завершения SQL-операции. Никаких изменений глобального хранилища сертификатов Windows. Настройки и путь передаются отдельным аргументом base64(JSON) без пароля. Пароль вводится непосредственно в интерактивной консоли дочернего процесса без эха, через SecureString, не через аргументы, переменные среды, файлы и stdout. Код stdout предназначен только для приватного канала родителя, прямой запуск исполнителя пользователем не является штатным способом выгрузки. Родитель проверяет exit code, хеш SQL-профиля и режим результата. Неудачное выполнение не создаёт пакет. Не защищаем от компрометации самого хоста, администратора или процессов того же доверенного пользователя.

Проверка SQL-прав и структуры в новом исполнителе выполняется до финансового запроса на том же физическом SQL-соединении. Проверяются все восемь результатов существующего guard; запрещены недостающие и повторные проверки, NULL, неуспешное значение и дополнительные результаты. Денежные значения возвращаются строками, даты/число операций сохраняют прежний контракт. Общее формирование и атомарная запись пакета остались в PowerShell, приёмник и SQL-профили не изменялись. Передача по сети/служба/интеграция с отчётами остаются вне дельты.

### Первоначальное подтверждение pin и ротация

Сертификат из Schannel или из сетевого подключения — лишь наблюдавшийся кандидат. Его получение само по себе не доказывает, что это подлинный сервер IDENT. До доверенной установки требуется подтверждение подлинности по независимому каналу. Если такое подтверждение невозможно, самостоятельное решение о первом доверии (TOFU, trust on first use) с явно зафиксированным остаточным риском может принимать только владелец отдельным разрешением; по умолчанию оно НЕ разрешено. Повторное наблюдение на другой машине уменьшает неопределённость, но не доказывает подлинность. Исходники не содержат автоматического enrollment, загрузки сертификата из сети, доверия по имени fallback, замены pin при ошибке либо TrustServerCertificate=True.

Резервный сертификат SQL Server может меняться после перезапуска. Тогда подключение с прежним pin должно завершиться отказом. Новый публичный DER и его SHA-256 проверяются и утверждаются заново; непрерывность работы не гарантируется без стабильного сертификата.
