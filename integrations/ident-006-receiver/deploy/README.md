# IDENT-006B — guarded server installation, SOURCE-ONLY

Базовый аудированный приёмник IDENT-006A: HEAD f1d0749dc9127af826a67720cfcfb2a307eba81c, TREE ac38a2cba78837d6df596248561f38c11159f334. Все восемь файлов 006A остаются побайтно неизменными. Данная дельта только добавляет deploy/. Не является разрешением на установку, HTTPS-публикацию, передачу реальных данных или изменение действующего AZ BAZE.

## Решение

Один отдельный экземпляр для одной утверждённой организации, source_id и stream_id. Сборщик на EX-18-4 уже физически проверен; его первый локальный пакет остаётся на компьютере. Идентификаторы надо будет взять именно из этого пакета, не генерировать новые при каждом запуске. Реальные значения не входят в Git. Секрет токена генерируется на стороне отправителя из 32 случайных байтов; на сервер доставляется только SHA-256 64-символьного hex-токена. Пароль SQL на сервер не передаётся. Конфигурация фиксирует organization_id, source_id, stream_id, source_timezone, token_sha256, max_store_bytes, min_free_bytes. До передачи реального пакета отдельное согласование.

Действующий AZ BAZE (по исходному коду: az-baze-auth.service, 127.0.0.1:8001/health, /opt/az-baze-auth, /var/lib/az-baze/auth.db, /etc/az-baze, /var/www) не обновляется, не останавливается, не мигрирует. Проверка его /health перед и после изменений. Это проверка доступности, не доказательство отсутствия всех возможных побочных эффектов. В этой работе live-сервер не опрашивается и не меняется.

Новые отдельные ресурсы:
- /opt/az-ident006b/app и /opt/az-ident006b/venv — root-owned, без права изменения сервисом. Две заранее проверенные wheel-зависимости (gunicorn 23.0.0, packaging 26.4) установлены offline с --require-hashes, --no-index и --no-deps. Хеши wheel из PyPI JSON API соответствующих версий. Фиксация версий и pip check не являются полной проверкой известных CVE; актуальную проверку уязвимостей зависимостей и системного Python/SQLite выполнить перед реальным допуском.
- /etc/az-ident006b/config.json — root:az-ident-recv 0640, отдельный каталог 0750; только verifier токена.
- /var/lib/az-ident006b/state — отдельный пользователь az-ident-recv, 0700, SQLite 0600; не auth.db. /var/lib/az-ident006b/deploy — root-only резервные копии и журнал публикации.
- az-ident006b.socket и az-ident006b.service — системный автозапуск обоих, Restart=on-failure, отдельный системный пользователь без shell, ограничение ресурсов и capabilities, private network, AF_UNIX only, read-only system, закрытые пути действующей AZ BAZE. Nginx worker должен работать с группой www-data; это проверяемое требование, а не предположение о live. Socket root:www-data 0660. Nginx не получает права чтения БД/конфигурации. Сервис не состоит в www-data. Системный launcher проверяет LISTEN_PID, LISTEN_FDS=1, точный путь, тип и ACL перед exec Gunicorn; при ошибке не открывает запасной TCP listener.
- Два exact location на существующем HTTPS-хосте, без нового домена, сертификата, DNS, внешнего SQL-порта. Разрешён только явно утверждённый hostname и совпадающий SNI; даже другие имена того же server block не получают API. TLS завершается действующим Nginx, сертификат при контрольном запросе проверяется штатным системным доверием и именем. Nginx не передаёт произвольные заголовки, передаёт Authorization, тип/длину тела и собственный HTTPS marker; 512 KiB limit, buffering, timeouts, per-IP rate/connection limits, без access log для новых маршрутов. Ошибки Nginx до gateway могут иметь HTML body; отправитель должен учитывать HTTP status и валидировать ACK целиком. Ограничение не является полной DDoS-защитой. Не публиковать receiver отдельно на TCP, не ослаблять TLS.

## Файлы и режимы

installer.py — первый install только, root Linux, обязательный exact hostname и SHA-256 /etc/machine-id; явная команда подтверждения для каждого mutating action. Требуется доверенный root-owned каталог исходников, предварительно проверенный по неизменяемому Git HEAD и SHA-256 самого installer.py до запуска. Внутри повторно проверяется externally supplied SHA-256 INSTALL-MANIFEST.json, затем каждый файл, включая строгие известные хеши четырёх runtime файлов 006A. Самопроверка не заменяет внешний хеш bootstrap. Установщик не скачивает пакеты, не ставит системное ПО и не угадывает настройки. В CI подготовка prerequisites отдельно на временном runner. Нужны Python >=3.10 с venv, системные systemd/Nginx, root, существующий AZ health endpoint, проверенный offline wheelhouse, действующий сертификат и подтверждённый Nginx vhost. Никаких ключей сертификата или токенов в Git.

Пример интерфейса (плейсхолдеры, НЕ команда для исполнения в Production):
  python3 -B deploy/installer.py --expected-host HOST --machine-id-sha256 MACHINE_HASH --manifest-sha256 MANIFEST_HASH plan-stage --config /root/private-config.json --wheelhouse /root/verified-wheels
  ... --confirm IDENT-006B-STAGE stage --config ... --wheelhouse ...
  ... plan-https --vhost /etc/nginx/sites-available/APP.conf --https-host APPROVED_HOST --vhost-sha256 OLD_HASH
  ... --confirm IDENT-006B-PUBLISH publish --vhost ... --https-host ... --vhost-sha256 ...
  ... --confirm IDENT-006B-UNPUBLISH unpublish
  ... --confirm IDENT-006B-RECOVER recover

plan-stage и plan-https — только проверка; не создают БД, пользователей, конфиги, не запускают сервисы. Чтение локальной health и HTTPS — не финансовый запрос. stage требует отсутствия всех целевых путей, UID/GID, units; создаёт только новые ресурсы, проверяет зависимости, init отдельной БД, Unix HTTP 401 без токена, включает autostart. При ошибке прекращает работу, останавливает/отключает только созданные units, сохраняет частично созданные файлы для диагностики, не удаляет данные. Повторная установка поверх существующей не предусмотрена; обновления и удаление отдельным проверенным механизмом.

plan-https требует существующий работающий TLS-host, проверенный exact vhost SHA-256, файл root-owned regular без symlinks/hardlinks в sites-available или conf.d, загруженный один раз по nginx -T. Выбирает ровно один прямой server block с именем и исключительно явными TLS listen 443 ssl. Вставляет только один include, сохраняя все исходные байты. Смешанные HTTP/HTTPS, неявные listen, server-level rewrite/return/if/error_page, неразбираемый синтаксис, уже существующие exact маршруты/включение, конфликты server_name блокируют запуск. Это намеренно консервативный редактор, не полный универсальный парсер Nginx; если реальная конфигурация отличается, подготовить отдельную точечную дельту после READ-ONLY обследования. Никакой правки по догадке.

publish создаёт root-private backup оригинала и кандидата с хешами, durable pending record, два новых snippet-файла (http context и locations), затем атомарно заменяет только согласованный vhost после повторной проверки SHA. nginx -T/-t, проверка загрузки каждого include, reload только Nginx, проверка через локальный HTTPS с реальным SNI и проверкой доверия сертификату: новый status без token обязан вернуть JSON 401, прежний корневой маршрут — исходный статус, AZ health — ok. Сохраняет active record. В случае ошибки пытается восстановить оригинал и удалить только собственные совпадающие по SHA snippets, повторяет nginx -t/reload/health. Не затирает параллельные изменения. Все backup остаются. unpublish выполняет тот же guarded rollback, оставляя БД и сервис; recover — явное восстановление незавершённой публикации по pending record. При внешнем изменении конфигурации, ошибке rollback или прерывании требуется операторская проверка; нет автоматического разрешения конфликта и нет обещания нулевого downtime при отказах инфраструктуры. Перед реальной публикацией необходимо исключить параллельное изменение Nginx, проверить backup (в том числе ACL/метаданные), согласовать время reload, состояние остальных сайтов. Installer проверяет байты, owner/group/mode и хеши; расширенные ACL, xattrs/SELinux, произвольные кастомные Nginx layout не покрыты. Для первого допуска требуем обычные файлы без таких специальных метаданных.

## Приёмка

Тесты из корня: python3 -m unittest discover -s tests -v; python3 -m unittest discover -s deploy/tests -p test_deploy.py -v. Синтетический disposable GitHub Actions fixture устанавливает prerequisites, stand-in существующей health, локальный CA/сертификат с двумя тестовыми именами, проверяет installer на root-owned staging, не читает и не использует реальные данные. Проверяются stage-plan, host guard, systemd units/socket ACL, отсутствие права Nginx читать конфиг/БД, HTTPS certificate verification, отказ без token, отдельный host/SNI, размер запроса, точный ACK, повтор, намеренный Nginx-конфликт и rollback, автоматический restart при SIGKILL, сохранение пакета после restart и unpublish. Логи и verdict CI должны проверяться фактически. Лабораторный сертификат добавляется в trust store только на одноразовом runner; реальный сервер не меняет trust store. Полная перезагрузка физического сервера и реальная конфигурация Nginx/сертификат в этой дельте не проверяются.

После независимого аудита: отдельное разрешение на READ-ONLY live preflight и подготовку установки; проверить место/квоту, шифрование диска, резервное копирование, live vhost и версию systemd/Nginx, источники регистрации. Затем отдельный допуск на stage, затем на publish. Передавать только синтетические пакеты до явного разрешения реального источника. Не переключать отчёты без сверки. Windows-служба, DPAPI, постоянная sequence, отправитель, дозагрузка, BIOS power restore и полная проверка автономного восстановления EX-18-4 относятся к следующей дельте, не объявляются готовыми.
